# PRD-06 — کیفیت، امنیت و استقرار

## هدف
قابل انتشار بودن محصول باید با شواهد قابل تکرار اثبات شود، نه صرفاً با وجود تست‌ها یا موفقیت اجرای محلی.

## نیازمندی‌های کیفیت

### FR-01: دروازه CI
هر PR باید lint، typecheck، test، بررسی معماری، تست‌های دیتابیس/یکپارچگی موجود و buildهای مرتبط را اجرا کند.
- **سناریو:** یک Promise مدیریت‌نشده باعث شکست lint می‌شود.
- **پذیرش:** CI شکست را گزارش می‌کند؛ خطا فقط برای سبزشدن با ignore/void کورکورانه پنهان نمی‌شود.

### FR-02: آزمون مهاجرت دیتابیس
مهاجرت‌ها باید روی دیتابیس تمیز و نسخه پشتیبان/نسخه موجود به‌صورت کنترل‌شده آزموده شوند.
- **سناریو:** محیط تست از دیتابیس خالی بالا می‌آید.
- **پذیرش:** تمام migrationها بدون دستکاری دستی موفق می‌شوند و schema مورد انتظار ایجاد می‌شود.

### FR-03: پیکربندی محیط
نام متغیرهای محیطی بین config، Docker Compose، Dockerfile، CI و runbook یکسان باشد.
- **سناریو:** سرویس در production با MEDIA_ROOT اجباری اجرا می‌شود.
- **پذیرش:** متغیر صحیح در کانتینر موجود است؛ سرویس به‌علت نام ناسازگار env از کار نمی‌افتد.

### FR-04: سلامت و آمادگی
health endpoint زنده‌بودن process را از readiness وابستگی‌ها جدا کند.
- **سناریو:** دیتابیس در دسترس نیست.
- **پذیرش:** readiness شکست می‌خورد و علت بدون افشای secret قابل تشخیص است.

### FR-05: مشاهده‌پذیری
خطاهای غیرمنتظره، شکست پیامک، شکست وب‌هوک، وضعیت jobها و خطاهای ذخیره‌سازی ثبت شوند.
- **سناریو:** درگاه پیامک پاسخ ناموفق می‌دهد.
- **پذیرش:** رخداد قابل پایش است، اطلاعات حساس ثبت نمی‌شود و وضعیت موفق کاذب گزارش نمی‌شود.

### FR-06: پشتیبان‌گیری و بازیابی
دیتابیس اصلی، دیتابیس CMS و رسانه‌ها باید بر اساس RPO/RTO مورد تأیید پشتیبان‌گیری شوند. بازیابی باید دوره‌ای آزمایش شود.
- **سناریو:** محیط آزمایشی از بک‌آپ بازیابی می‌شود.
- **پذیرش:** شمارش و یکپارچگی داده‌های نمونه بررسی و نتیجه ثبت می‌شود.

### FR-07: انتشار و rollback
انتشار نسخه باید شامل smoke test و مسیر rollback مستند باشد.
- **سناریو:** smoke test پس از deploy شکست می‌خورد.
- **پذیرش:** نسخه قبلی یا روش بازیابی مشخص است و تصمیم توقف انتشار ثبت می‌شود.

## حداقل چک‌لیست انتشار
- CI سبز روی commit دقیق انتشار.
- secrets تولیدی مستقل، قوی و بدون fallback قابل حدس.
- نام envها در config و compose هم‌خوان.
- migration و health/readiness موفق.
- تست مالکیت منابع و دسترسی عمومی CMS.
- پیامک در محیط واقعی با تأیید provider test شده باشد.
- بک‌آپ هر دو دیتابیس و رسانه‌ها و آزمون restore مستند باشد.
- دامنه‌های عمومی، CORS، cookie/security headers و webhook secrets بررسی شوند.
- smoke test صفحه اصلی، مقاله، ثبت استعلام، پنل مشتری و پنل مدیریت اجرا شود.

## معیار خروج
هیچ P0 امنیتی باز نماند؛ CI سبز باشد؛ شواهد smoke test، restore و پیکربندی تولید ثبت شده باشد. شمار تست‌های README به‌تنهایی معیار پذیرش نیست.
