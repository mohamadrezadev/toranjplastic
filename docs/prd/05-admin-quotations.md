# PRD-05 — پنل مدیریت، کارکنان و پیش‌فاکتور

## هدف
ایجاد جریان کاری قابل کنترل برای بررسی استعلام‌ها، ارجاع به کارکنان، ارتباط با مشتری و ارائه پیشنهاد تجاری دقیق.

## نیازمندی‌های عملکردی

### FR-01: صف استعلام‌ها
کارکنان مجاز بتوانند استعلام‌ها را فیلتر و بر اساس وضعیت، تاریخ، نوع درخواست و مسئول بررسی کنند.
- **سناریو:** کاربر Sales استعلام‌های UnderReview را باز می‌کند.
- **پذیرش:** فقط داده‌های مجاز نقش او نمایش داده می‌شود؛ فیلتر و صفحه‌بندی معتبر است.

### FR-02: تخصیص و گردش وضعیت
تخصیص مسئول و تغییر وضعیت باید طبق انتقال‌های مجاز و سطح دسترسی باشد.
- **سناریو:** Operator تلاش می‌کند وضعیت را به Quoted تغییر دهد، در حالی که مجوز صدور پیشنهاد ندارد.
- **پذیرش:** تغییر رد می‌شود و تاریخچه بدون تغییر باقی می‌ماند.

### FR-03: یادداشت داخلی
کارکنان مجاز بتوانند یادداشت داخلی ثبت کنند. این یادداشت از پیام مشتری و تمام پاسخ‌های عمومی API جدا باشد.
- **سناریو:** Customer درخواست جزئیات یک استعلام را می‌کند.
- **پذیرش:** پاسخ فقط اطلاعات قابل مشاهده مشتری را برمی‌گرداند.

### FR-04: مدیریت کارکنان
Admin بتواند کارکنان را ایجاد/غیرفعال و نقش‌های مجاز را مدیریت کند. کاربر نباید بتواند خودش را به نقش بالاتر ارتقا دهد.
- **سناریو:** Sales درخواست API تغییر نقش خود را می‌فرستد.
- **پذیرش:** پاسخ رد می‌شود و رخداد قابل ممیزی است.

### FR-05: پیش‌فاکتور
کاربر مجاز بتواند اقلام و شرایط پیش‌فاکتور را وارد و پیش‌نمایش را قبل از صدور بررسی کند. فرمول‌ها و مالیات باید با تصمیم مستند مالی اجرا شوند.
- **سناریو:** کارشناس پیش‌فاکتور را برای استعلام آماده می‌کند.
- **پذیرش:** جمع ردیف‌ها، تخفیف و مالیات با آزمون‌های مرزی محاسبه می‌شوند؛ سند پیش از صدور نهایی وضعیت draft دارد.

### FR-06: صدور PDF
نسخه صادرشده باید شماره، تاریخ، مشخصات طرفین، اقلام، مبالغ، شرایط و وضعیت اعتبار را طبق الگوی تأییدشده نمایش دهد.
- **سناریو:** پیش‌فاکتور صادرشده توسط مشتری دانلود می‌شود.
- **پذیرش:** فقط مشتری مجاز به همان سند دسترسی دارد؛ PDF با داده جاری و نسخه صادرشده سازگار است.

### FR-07: ثبت رویدادهای تجاری
صدور، لغو یا اصلاح پیش‌فاکتور و تغییرات مهم استعلام باید تاریخچه داشته باشد.
- **سناریو:** سند صادرشده نیازمند اصلاح است.
- **پذیرش:** سند قبلی بی‌ردپا بازنویسی نمی‌شود؛ روش اصلاح/نسخه‌بندی مطابق سیاست مالی مستند است.

## الزامات امنیتی
- تمام عملیات مدیریتی در بک‌اند مجوزدهی شوند.
- داده‌های مالی و یادداشت داخلی فقط به نقش‌های مجاز برسند.
- خروجی PDF و فایل‌های تولیدشده در storage خصوصی یا پشت کنترل دسترسی باشند.
- لاگ ممیزی شامل عامل، زمان، نوع عملیات و شناسه رکورد باشد، نه secret یا محتوای غیرضروری حساس.

## تصمیم‌های نیازمند تأیید
- فرمت شماره پیش‌فاکتور.
- قواعد تخفیف، ارزش افزوده، گردکردن، واحد پول و اعتبار زمانی سند.
- نقش‌های مجاز برای صدور نهایی و لغو/اصلاح.
- آیا هر اصلاح باید سند جدید ایجاد کند یا نسخه‌بندی در همان رکورد کافی است.

## معیار پذیرش
- تست محاسبات با اعداد مرزی و گردکردن.
- تست مجوزهای Admin/Sales/Operator/Customer.
- تست PDF، دسترسی بین‌کاربری و حفظ تاریخچه.
