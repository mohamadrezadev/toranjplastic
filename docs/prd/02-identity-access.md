# PRD-02 — هویت، نشست و کنترل دسترسی

## هدف
محافظت از حساب‌ها و داده‌های تجاری و اطمینان از اینکه هر کاربر فقط منابع مجاز را مشاهده یا تغییر می‌دهد.

## نیازمندی‌های عملکردی

### FR-01: ثبت‌نام و ورود
فرایندهای ورود و ثبت‌نام باید با جریان موجود در مخزن هماهنگ شوند؛ روش‌های ورود و قواعد تأیید شماره تماس نباید بدون تصمیم محصول تغییر کنند.
- **سناریو:** کاربر معتبر وارد می‌شود و به پنل خود هدایت می‌شود.
- **پذیرش:** خطاهای اعتبارسنجی فارسی هستند؛ پیام خطا وجود یا عدم وجود حساب را بیش از حد افشا نمی‌کند.

### FR-02: مدیریت نشست و توکن
توکن‌ها و نشست‌ها باید مطابق پیاده‌سازی واقعی امن شوند؛ اسرار فقط از environment/secret manager خوانده شوند، نه از مقادیر پیش‌فرض قابل حدس.
- **سناریو:** secret ضروری در محیط production تنظیم نشده است.
- **پذیرش:** سرویس fail-fast می‌کند و با secret شناخته‌شده یا ناامن بالا نمی‌آید.

### FR-03: نقش‌ها و مجوزها
نقش‌های Customer، Sales، Operator و Admin در بک‌اند اعمال شوند. مجوز هر عملیات حساس در سمت سرور بررسی شود.
- **سناریو:** Customer درخواست تغییر نقش خود یا مشاهده endpoint مدیریتی می‌دهد.
- **پذیرش:** پاسخ 403/404 مطابق سیاست API؛ هیچ تغییری انجام نمی‌شود.

### FR-04: مالکیت منابع
تمام queryهای استعلام، پیام، پیش‌فاکتور و فایل باید به هویت کاربر و مجوز او محدود شوند؛ شناسه غیرقابل حدس به‌تنهایی مجوز نیست.
- **سناریو:** مشتری A شناسه استعلام متعلق به مشتری B را در URL وارد می‌کند.
- **پذیرش:** داده مشتری B، پیوست‌ها و وجود اطلاعات محرمانه افشا نمی‌شود.

### FR-05: مدیریت کارکنان
فقط Admin مجاز می‌تواند کارکنان و نقش‌هایشان را مدیریت کند. تغییرات نقش باید قابل ممیزی باشد.
- **سناریو:** کاربر Sales تلاش می‌کند حساب Admin جدید بسازد.
- **پذیرش:** عملیات رد می‌شود و رخداد امنیتی بدون ذخیره اطلاعات حساس ثبت می‌شود.

## امنیت و حریم خصوصی
- اصل کمترین دسترسی؛ عدم اعتماد به role یا user ID ارسالی از کلاینت.
- عدم ثبت رمز، OTP، توکن، secret، متن کامل اسناد خصوصی یا اطلاعات حساس در لاگ.
- محدودسازی نرخ برای مسیرهای ورود/OTP و جلوگیری از brute-force.
- کوکی‌ها در صورت استفاده از cookie باید HttpOnly، Secure در HTTPS و SameSite مناسب داشته باشند.
- endpointهای خصوصی با cache عمومی ناسازگارند؛ از `no-store` برای پاسخ‌های حساس استفاده شود.

## معیار پذیرش
- تست‌های مثبت و منفی برای هر نقش و هر منبع حساس.
- آزمون دسترسی بین‌کاربری برای استعلام، پیام، پیش‌فاکتور و رسانه.
- آزمون تنظیمات production با secret مفقود.
- مستندکردن روش recovery حساب و چرخش secret، بدون درج مقادیر واقعی.
