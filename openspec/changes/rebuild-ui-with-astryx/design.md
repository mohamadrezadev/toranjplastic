## Context

The frontend is a Next.js 16 / React 19 application with a Toranj-owned semantic token registry, CSS Modules, a small typed primitive layer, Persian RTL document defaults, light/dark bootstrap logic, Vitest component coverage, and Playwright end-to-end tests. Those foundations are sound, but presentation and interaction patterns are repeated across public, auth, inquiry, customer, and admin surfaces. Astryx provides a broader accessible component catalog plus a CLI designed to give people and agents the same component, template, theme, diagnostic, and upgrade guidance.

This is a cross-cutting frontend migration. Product contracts, server authorization, private-data behavior, CMS content, and backend APIs remain authoritative and unchanged. The repository contract and OpenSpec remain higher authority than any guidance generated by Astryx.

## Goals / Non-Goals

**Goals:**

- Establish one pinned, reproducible Astryx foundation for supported shared controls and compositions.
- Preserve Toranj's Persian RTL, petroleum-and-stone visual identity, bundled typography, light/dark preference, mobile-first behavior, and accessibility requirements.
- Make the official Astryx CLI workflow available to Codex and human contributors through project-local commands and generated guidance.
- Migrate the UI in independently verifiable phases without a flag day or a mixed partially styled screen.
- Preserve Toranj domain ownership, architecture boundaries, route behavior, server/client boundaries, and security controls.

**Non-Goals:**

- Forking Astryx, copying its repository wholesale, or depending on unpublished Lab packages.
- Introducing StyleX authoring into Toranj application code during the initial migration.
- Swizzling components by default or editing files inside `node_modules`.
- Changing backend APIs, DTOs, authentication, authorization, cache policy, indexing policy, CMS models, inquiry states, or business workflows.
- Adding ecommerce, automatic pricing, live inventory, delivery promises, capacity claims, or unverified content.
- Recreating every Astryx example or adopting components that no Toranj screen needs.

## Decisions

### 1. Consume published packages and the project-local CLI

`@astryxdesign/core`, the selected published theme package, and `@astryxdesign/cli` will use the same exact version. The root or frontend package will expose a deterministic `astryx` script that invokes the installed CLI directly. Implementation starts from the latest reviewed stable 0.x release available at apply time and records that exact version in the lockfile.

This follows Astryx's supported distribution and upgrade path. Copying source from the upstream repository was rejected because it would discard release tooling, diagnostics, codemods, and provenance. A global CLI was rejected because it is not reproducible in CI.

### 2. Use the prebuilt CSS distribution for the initial adoption

The frontend will import Astryx reset, component CSS, and the selected base theme in the documented layer order. A Toranj theme stylesheet will override supported theme variables and targets using output produced or validated by the Astryx theme workflow. Toranj application code will continue to use CSS Modules and semantic Toranj tokens for product-specific composition.

`@astryxdesign/build` and product-side StyleX authoring are excluded initially. They become necessary only if a separately reviewed change approves source builds or a swizzled component. This keeps Next.js/Turbopack configuration and the current CSS Module pipeline stable.

### 3. Keep the root layout server-rendered and isolate providers

The root document will retain `lang="fa"`, `dir="rtl"`, pre-paint theme resolution, local fonts, metadata, and private-route behavior. Any Astryx Theme or Link provider that requires client execution will live in a narrow `providers` client boundary below the server-rendered layout; it will not convert the application shell or routes into broad client components.

The Toranj theme resolver remains the source of the effective light/dark preference. Astryx consumes that resolved state rather than introducing a second preference store.

### 4. Preserve the four Toranj UI layers

The existing `tokens -> primitives -> domain-components -> screens` dependency direction remains authoritative. Astryx is an implementation dependency of tokens/primitives and may be composed by domain components. Screens and feature modules consume Toranj public component entry points and do not deep-import Astryx internals.

Compatibility adapters will preserve frequently used Toranj props while a screen is migrated. Adapters must remain thin: semantic mapping, Persian defaults, and compatibility only; product rules and network access remain outside primitives. Once a surface is migrated and call sites can use the preferred API safely, obsolete adapter paths are removed.

### 5. Adopt components by need, using the official discovery workflow

For each migrated surface the implementer will run the project-local equivalents of `astryx build`, `astryx search`, `astryx component`, and `astryx template` before composing the page. Only the returned public packages, templates, and components may be adopted. Generated examples are starting points and must be reconciled with current Toranj specs and real API data.

The initial representative set covers actions, fields, selection, feedback, navigation, modal/layer behavior, responsive collections, pagination, and data presentation. Toranj retains domain components for inquiry state, quotations, customer messaging, media provenance, and authorization-sensitive operations.

### 6. Treat generated agent guidance as a managed subordinate section

`astryx init` will be run from the repository root during implementation. Its marked Astryx block may be committed only after review confirms that it does not replace or weaken the existing `AGENTS.md` contract. Repository source-of-truth order, OpenSpec lifecycle, Persian RTL rules, security constraints, and product non-goals remain higher priority. Generated guidance outside marked blocks will not be accepted.

### 7. Do not swizzle without an explicit exception

Composition, supported theme variables, documented props, and `className`/style extension points are the default customization mechanisms. A swizzle is permitted only when a required, spec-backed behavior cannot be achieved through public APIs. The exception must record the component, reason, upstream version, copied files, ownership, tests, and future upgrade plan in the change artifacts or an ADR before source is copied.

### 8. Verify at component, surface, and completed-build levels

Component tests will cover semantics, Persian labels, loading/disabled/error behavior, keyboard operation, and axe checks. Playwright will cover representative flows in RTL, light/dark themes, and widths 360, 390, 768, and 1280, including one pixel around material breakpoints where required by existing specs. Visual references will be captured for the noindex brand/component preview and migrated surfaces. The final gate includes existing lint, typecheck, unit, architecture, E2E, and build commands plus Astryx doctor against source and the completed build when supported by the installed CLI.

## Risks / Trade-offs

- **0.x releases can introduce breaking changes at minor versions** -> Pin all Astryx packages exactly, upgrade them together, review release notes/codemods, and make upgrades separate verified work.
- **RTL coverage can be uneven in complex components** -> Test every adopted component with Persian content and real keyboard/pointer behavior; reject or locally compose around any component that fails instead of assuming library-wide RTL support.
- **Base reset or theme CSS can alter existing screens before migration** -> Introduce CSS layers and the theme in the component preview first, then migrate complete surfaces in order; do not globally ship a half-migrated cascade.
- **Provider use can expand client bundles or cause hydration differences** -> Keep a narrow provider boundary, preserve server components, and compare build output and hydration console errors before rollout.
- **Adapters can become permanent abstraction debt** -> Give each adapter an owner and removal task; forbid product logic in adapters and track remaining legacy call sites.
- **A large UI rewrite can regress product/security behavior** -> Keep backend and data contracts untouched, migrate by surface, and retain the existing authorization, ownership, no-store, noindex, and failure-path tests.
- **Generated agent instructions can conflict with repository policy** -> Commit only the marked reviewed Astryx section and assert precedence explicitly.
- **Visual consistency may be lost when mixing legacy and Astryx controls** -> Complete one bounded surface at a time and do not expose mixed visual systems within the same user flow.

## Migration Plan

1. Record baselines: current screenshots, bundle/build output, accessibility checks, route inventory, primitive usage, and critical user flows.
2. Add exact-version packages and CLI script; run and review `astryx init`; verify the dependency and generated guidance without migrating production screens.
3. Establish CSS layer order, provider boundary, Toranj theme mapping, local fonts, direction behavior, and the noindex component/brand preview.
4. Implement and verify thin primitive adapters for the representative component set.
5. Migrate public shell and public content surfaces as one coherent phase.
6. Migrate auth and inquiry creation surfaces.
7. Migrate customer account, inquiry detail, messaging, and quotation-response surfaces.
8. Migrate admin shell, content/media, inquiry/quotation, and staff management surfaces.
9. Remove unused legacy styles/adapters after repository-wide usage checks; run all quality gates and completed-build doctor.

Each phase is rollbackable by reverting its route/component composition and associated theme mappings while retaining the pinned dependency. If the foundation itself fails RTL, accessibility, hydration, or build acceptance, remove the packages and CSS/provider integration and restore the recorded baseline; no backend rollback is required.

## Open Questions

- The exact published Astryx version and base theme will be confirmed at implementation start from the reviewed release; all selected packages must share that version.
- Component-by-component suitability, especially modal layers, calendar/date inputs, tables, and directional navigation, remains an evidence question resolved by the preview and automated RTL checks rather than assumed in advance.
