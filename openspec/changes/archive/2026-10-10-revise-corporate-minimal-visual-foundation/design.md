## Context

The current frontend already centralizes visual decisions in semantic CSS custom properties and composes shared UI, feedback, and navigation components. This makes a visual revision low-risk, but the present palette is dominated by a warm industrial orange and the declared `Vazirmatn` family is not delivered to the browser; screenshots therefore reflect a system fallback rather than an intentional type system.

The product owner selected a corporate-minimal direction. The change must improve the actual rendered UI without modifying routes, content approval boundaries, backend behavior, or the no-ecommerce contract. Logo, photography, contact data, and final marketing content remain unapproved.

## Goals / Non-Goals

**Goals:**

- Establish a calm corporate-minimal palette with neutral surfaces, deep navy typography, and one controlled blue action accent.
- Deliver a consistent Persian typeface in the application bundle and prevent layout dependence on an unavailable local font.
- Reduce visual noise through lighter borders, restrained shadows, tighter radius use, and clearer whitespace hierarchy.
- Update every shared primitive and current public surface through semantic tokens rather than page-local color replacements.
- Preserve accessible focus, status distinction, contrast, RTL behavior, touch targets, reduced motion, and the four required viewports.

**Non-Goals:**

- Creating or approving a final logo, brand guidelines, illustrations, photography, contact details, or marketing claims.
- Changing public routes, page copy meaning, backend APIs, persistence, authentication, inquiry workflows, or authorization.
- Introducing a theme switcher, dark mode, animation system, CSS framework, ecommerce, payment, inventory, or automatic pricing.

## Decisions

### 1. Use a navy, blue, and neutral token family

The visual baseline will use deep navy for brand/text hierarchy, a clear corporate blue for interactive emphasis, near-white cool-neutral canvases, white surfaces, slate secondary text, and low-contrast cool borders. Status colors remain independent from the brand accent.

The initial implementation values will be reviewed in the running application and contrast tests, with semantic roles kept stable even if an individual hex value needs tuning. Existing industrial/kitchen section accents remain available only where domain identity is required; they will not drive global calls to action.

**Alternative considered:** retain the current orange as the primary CTA. It is rejected because it keeps the industrial warmth the product owner explicitly declined and competes with warning states.

### 2. Bundle Estedad Variable as the Persian UI font

The frontend will use `@fontsource-variable/estedad` and import its CSS through the root application stylesheet. The semantic Persian font token will prefer `"Estedad Variable"`, followed by Tahoma, Arial, and sans-serif. The Latin/data stack stays isolated for technical identifiers.

Bundling through the package lock makes local, CI, and production rendering deterministic and avoids runtime requests to a third-party font service. Only the styles required by the package will be imported; no remote font or tracking endpoint is introduced.

**Alternative considered:** use `next/font/google`. It is rejected because builds would depend on external font retrieval. Keeping the unavailable `Vazirmatn` declaration is also rejected because it reproduces the current fallback inconsistency.

### 3. Restyle by semantic role, not component overrides

`tokens.css` remains the only source for palette, typography, radius, border, shadow, focus, and motion values. Component CSS Modules will be adjusted only when their visual structure is inherently heavy, such as filled header branding, strong card shadows, high-saturation badges, or oversized rounded containers.

The public page will remove decorative industrial motifs that do not support the corporate-minimal direction. Layout structure, content order, and component APIs remain stable.

**Alternative considered:** add a second theme class beside the existing style. It is rejected because the product owner selected one direction and a dormant theme would add untested maintenance cost.

### 4. Keep brand assets explicitly provisional

The textual Toranj mark stays in place with a restrained geometric monogram treatment. It must not be represented as a finalized logo. No logo file, PWA icon, or unverified company asset will be generated by this change.

### 5. Verify rendered typography and visual states

Static tests will assert that the Persian font package is imported and the semantic font token names the delivered family. Component tests retain accessibility coverage for focus, disabled, loading, feedback, and form states. Playwright will capture the home page and a provisional inner page at 360, 390, 768, and 1280 pixels, assert the computed Persian font family, and continue checking overflow, navigation, `noindex`, and valid destinations.

Manual review will compare hierarchy, density, contrast-sensitive states, mixed RTL/LTR text, and the mobile drawer. Screenshot approval is visual evidence, not a replacement for functional assertions.

## Risks / Trade-offs

- **[The chosen font changes line wrapping and page height]** → Re-run all required viewport tests and tune line-height/measure rather than shrinking text below the established scale.
- **[A blue accent could feel generic]** → Keep the color system restrained and let typography, spacing, and future approved brand assets provide identity; do not invent decorative brand claims.
- **[Font dependency increases frontend payload]** → Use the variable package, inspect build output, and avoid loading unrelated font families or remote assets.
- **[Token changes can reduce status contrast]** → Keep status tokens independent and run automated accessibility assertions plus manual state review.
- **[Existing screenshots change broadly]** → Treat the change as an intentional visual migration and update only repository-owned evidence after review.

## Migration Plan

1. Add the font dependency and prove it is loaded by the root application.
2. Replace raw provisional palette and typography values while preserving semantic token names where possible.
3. Refine shared UI, feedback, and navigation styles, then remove page-specific decorative treatments.
4. Run component, build, and Playwright checks at all required widths; review new screenshots in the running application.
5. Keep all provisional public pages `noindex` and deploy without backend or database migration.

Rollback is a frontend-only revert of the font dependency, token values, and CSS Module adjustments. No stored data or external resource requires rollback.
